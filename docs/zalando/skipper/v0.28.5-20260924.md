Changes

fix: copyRequestHeader and copyResponseHeader drop all but the first header value (<a class="issue-link js-issue-link" data-error-text="Failed to load title" data-id="5546244343" data-permission-text="Title is private" data-url="https://github.com/zalando/skipper/issues/4287" data-hovercard-type="pull_request" data-hovercard-url="/zalando/skipper/pull/4287/hovercard" href="https://github.com/zalando/skipper/pull/4287">#4287</a>)

Symptom

<code>copyResponseHeader</code> drops cookies. Copying <code>Set-Cookie</code> from a backend  

that sets more than one cookie:

    r: * -> copyResponseHeader("Set-Cookie", "X-Backend-Set-Cookie") -> "http://backend"

Backend response:

    Set-Cookie: a=1; Domain=example.org
    Set-Cookie: b=2; Domain=example.org

What the client gets through the proxy:

    X-Backend-Set-Cookie: a=1; Domain=example.org

The second cookie is gone. Expected:

    X-Backend-Set-Cookie: a=1; Domain=example.org
    X-Backend-Set-Cookie: b=2; Domain=example.org

<code>copyRequestHeader</code> does the same to the request, so a route copying  

<code>X-Forwarded-For</code> forwards only the first hop. Copying a header onto  

itself is also destructive: <code>copyResponseHeader("Set-Cookie", "Set-Cookie")</code> reduces the header to its first value.

The documentation said the filter copies "value of a given request  

header". <code>Header.Get</code>/<code>Header.Set</code> only ever see one value, which is not  

how repeated headers work.

Cause

<code>filters/builtin/headerfilter.go</code>:

    headerValue := header.Get(f.key)
    if headerValue != "" {
        header.Set(f.value, headerValue)
    }

<code>Header.Get</code> returns the first value only, and <code>Header.Set</code> replaces the  

whole entry with the single value it is given, so everything after the  

first value is dropped.

Fix

Copy every source value onto the destination. If the source and  

destination names are the same (including case-insensitive matches such  

as <code>Set-Cookie</code> / <code>set-cookie</code>), leave the header unchanged so a  

self-copy is a no-op instead of a truncation.

Reproduction

<code>go1.27.1 windows/amd64</code>. Before, with <code>filters/builtin/headerfilter.go</code>  

at master and only the tests of this PR applied:

    $ go test ./filters/builtin -run TestCopyHeaderMultipleValues -v
    === RUN   TestCopyHeaderMultipleValues/request
        copy_test.go:188: failed to copy all request header values, got: ["10.0.1.1"], want: ["10.0.1.1" "10.0.2.1"]
    === RUN   TestCopyHeaderMultipleValues/response
        copy_test.go:210: failed to copy all response header values, got: ["a=1; Domain=example.org"], want: ["a=1; Domain=example.org" "b=2; Domain=example.org"]
    === RUN   TestCopyHeaderMultipleValues/response_onto_itself
        copy_test.go:229: copying a header onto itself dropped values, got: ["a=1; Domain=example.org"], want: ["a=1; Domain=example.org" "b=2; Domain=example.org"]
    --- FAIL: TestCopyHeaderMultipleValues (0.00s)

The <code>TestHeader</code> table cases for <code>copy all header values</code> go through the  

proxy and fail the same way: destination has <code>["foo"]</code> instead of  

<code>["foo" "bar"]</code>.

After:

    $ go test ./filters/builtin -run 'TestCopyHeaderMultipleValues|TestHeader|Test_copyFilter|Test_copySpec' -count=3
    ok  	github.com/zalando/skipper/filters/builtin

    $ go test ./filters/builtin
    ok  	github.com/zalando/skipper/filters/builtin

Existing single-value <code>copyRequestHeader</code> / <code>copyResponseHeader</code> cases  

pass before and after; they only ever use one value, which is why this  

went unnoticed.
