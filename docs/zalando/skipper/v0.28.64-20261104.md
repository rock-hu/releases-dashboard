Summary

Fixes a bug where a request could receive a response whose body had  

already been closed.

When several requests arrive for the same uncached content, Skipper  

tries to share one backend fetch. The first request is the <strong>leader</strong>;  

the others are <strong>followers</strong>. If the response cannot safely be shared -  

ex: private content - a follower fetches its own response instead.

The fixes make that separate fetch work correctly:

* <strong>Keep the body readable:</strong> copy the response content into memory  
  before closing the backend stream. Previously, the follower was handed  
  that stream just before it was closed.
* <strong>Reject broken or cancelled reads:</strong> incomplete content is no longer  
  treated as a successful response. Cancelling a follower also stops its  
  separate fetch or stalled body read, without cancelling the shared  
  leader fetch.
* <strong>Report cache misses correctly:</strong> a successfully fetched follower  
  response now gets <code>X-Cache-Status: MISS</code> and is counted exactly once in  
  miss metrics.

<code>HEAD</code> requests still return no body.

How to reproduce

* Issue overlapping RFC-mode requests for a private, non-storeable  
  response, then read the follower body after the fetch returns.
* Return an incomplete body, or cancel the follower after headers while  
  its body is stalled.
